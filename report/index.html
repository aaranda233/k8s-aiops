Resumen

Motivación, contribución y diferencial del trabajo

Los clusters Kubernetes en producción generan miles de eventos por minuto. Identificar cuándo un patrón de logs señala un fallo real —y diagnosticar su causa raíz de forma automática— sigue siendo un problema abierto en Site Reliability Engineering.

Las plataformas comerciales existentes (Dynatrace, Datadog, New Relic) resuelven el problema, pero envían los datos del cluster a servidores externos, lo que las hace inviables en entornos con restricciones de privacidad o normativas de datos.

Este trabajo propone un pipeline AIOps completamente local que integra colección de eventos en streaming, parsing online de logs, detección de anomalías no supervisada y diagnóstico con un modelo de lenguaje pequeño fine-tuneado para el dominio Kubernetes.

Capa 1 — Colección y Parsing de Logs

Watch API de Kubernetes para streaming en tiempo real + Drain3 para parsing online sin supervisión

Watch API

A diferencia del polling periódico, la Watch API mantiene una conexión HTTP chunked abierta indefinidamente. El API Server escribe un objeto JSON por línea conforme ocurren eventos en el cluster, sin necesidad de que el cliente vuelva a preguntar. El campo resourceVersion actúa como cursor de posición; si la conexión se interrumpe, el colector reconecta desde el último punto conocido garantizando entrega at-least-once.

# Fragmento de evento recibido por Watch API
{
  "type": "ADDED",
  "object": {
    "reason":  "BackOff",
    "message": "Back-off restarting failed container nginx in pod nginx-7d4f9c-xp2lm_production",
    "involvedObject": { "namespace": "production" },
    "metadata":      { "resourceVersion": "1847392" }
  }
}

Drain3 — Parsing Online de Templates

Los mensajes de log de Kubernetes contienen tokens variables — IPs, UUIDs, nombres de pods, contadores. Drain3 agrupa logs semánticamente similares en templates sustituyendo los tokens variables por <*>, y asigna a cada grupo un cluster_id entero. Este identificador es el feature que consume el detector de anomalías.

El algoritmo trabaja con un árbol de prefijos de profundidad 4. La similitud entre un log entrante y un template candidato se calcula como tokens coincidentes / tokens totales, con umbral de 0.4. No requiere batch previo; los templates se crean y actualizan en streaming conforme llegan los logs.

# Raw log → Template Drain3
# Entrada:
"Back-off restarting failed container nginx in pod nginx-7d4f9c-xp2lm_production"

# Salida:
template   = "Back-off restarting failed container <*> in pod <*>"
cluster_id = 42

Capa 2 — Detección de Anomalías

Isolation Forest no supervisado con reentrenamiento continuo sobre ventana deslizante

Ventanas temporales

Los logs se agregan en ventanas de 60 segundos. Cada ventana se convierte en un vector de frecuencias —cuántas veces apareció cada cluster_id en ese intervalo— normalizado con L1 para hacer la comparación invariante al volumen total de eventos.

Isolation Forest

El Isolation Forest detecta anomalías sin ejemplos etiquetados. La intuición es que los puntos anómalos son estadísticamente escasos y se aíslan con pocos cortes aleatorios en el espacio de features. El comportamiento normal, al ser denso, requiere muchos más cortes para aislarse. El score resultante se normaliza entre 0 y 1; valores por encima de 0.80 disparan la capa de diagnóstico.

ParámetroValorJustificación
n_estimators200Balance precisión / velocidad de entrenamiento
contamination0.05Se asume ≤ 5% de ventanas anómalas en operación normal
threshold0.80Score normalizado 0–1 para disparar alerta
bootstrap_windows10Ventanas iniciales para construir el baseline
rolling_window_size50Ventanas recientes para reentrenamiento deslizante
retrain_every_n5Frecuencia de reentrenamiento para adaptarse al drift

Tres fases de operación

Bootstrap: las primeras 10 ventanas se acumulan asumiendo comportamiento normal. Con ellas se entrena el modelo inicial.

Detección: cada nueva ventana recibe un score. Si supera el umbral, se activa la capa de diagnóstico.

Reentrenamiento: cada 5 ventanas, el modelo se reentrena con las últimas 50, descartando historia antigua. Esto permite que el sistema se adapte al comportamiento cambiante del cluster sin olvidar el pasado reciente. En cada reentrenamiento se recalcula una proyección PCA 2D del training set para visualización en el dashboard.

Capa 3 — Diagnóstico con SLM Fine-tuneado

Qwen2.5-1.5B-Instruct con QLoRA, cuantizado a GGUF Q8_0 para inferencia en CPU

Selección del modelo base

Se eligió Qwen2.5-1.5B-Instruct por tres razones: (1) tamaño suficientemente reducido para inferencia en CPU a latencia aceptable; (2) capacidad de seguir instrucciones estructuradas desde el modelo base; y (3) soporte del formato ChatML, que facilita el fine-tuning con datos de conversación en tres turnos.

Fine-tuning con QLoRA

El entrenamiento se realizó en una GPU NVIDIA A30 (24 GB VRAM) usando QLoRA: cuantización 4-bit NF4 del modelo base con adaptadores LoRA entrenables sobre todos los módulos de atención y proyección. Solo se entrenan ~5 millones de parámetros de un total de 1.5B (1.6%), lo que permite un entrenamiento eficiente en hardware limitado.

Alineación del SLM — DPO, ORPO y KTO

6 experimentos de alineación por preferencias · 8 modelos evaluados · 210 muestras ciegas · seed=99

El SFT v1 establece que el modelo aprende el formato estructurado ROOT CAUSE / KUBECTL, pero con un coste: la memorización reduce el vocabulario libre (Keyword% cae de 92.4% a 60.0%). La segunda fase del proyecto busca resolver esta tensión mediante técnicas de alineación por preferencias.

Tensión fundamental identificada: existe un trade-off empírico entre Parse% y Keyword% a lo largo de todos los experimentos. Los métodos que mejoran el vocabulario libre (DPO) destruyen el formato; los que aprenden formato (SFT) restringen el vocabulario. ORPO es el primer método que, por diseño matemático, optimiza simultáneamente ambas señales.

Direct Preference Optimization (DPO)

DPO (Rafailov et al., 2023) elimina la necesidad de un modelo de recompensa explícito. La pérdida se define directamente sobre pares chosen / rejected usando un cociente de log-probabilidades como reward implícita:

L_DPO = −log σ( β · log[P_θ(chosen)/P_ref(chosen)] − β · log[P_θ(rejected)/P_ref(rejected)] )

β      = peso de la divergencia respecto al modelo de referencia
P_ref  = modelo de referencia fijo (checkpoint antes del entrenamiento DPO)

Reward implícita: r(x,y) = β · log[ P_θ(y|x) / P_ref(y|x) ]
No hay evaluador externo — el cociente de log-probabilidades es la señal.

Experimento DPO v1 — problema de formato en rejected

El baseline qwen2.5:1.5b genera formato ROOT CAUSE/KUBECTL solo el 38.6% del tiempo. Al usar sus respuestas como rejected, el modelo aprende que el formato es la característica discriminante y lo evita:

Resultado: DPO v1 mejora Keyword% (82.9%) pero destruye Parse% (16.2%). El modelo aprendió que el formato diferencia bueno de malo — y lo evita.

1960 pares donde chosen y rejected comparten exactamente los mismos tokens de estructura. El gradiente de preferencia actúa solo sobre contenido semántico:

ORPO — Odds Ratio Preference Optimization

ORPO (Hong et al., 2024) combina la pérdida SFT y la pérdida de preferencia en un único paso, sin modelo de referencia separado. El término L_SFT actúa como ancla continua de formato durante todo el entrenamiento:

L_ORPO = L_SFT + λ · L_OR

L_SFT = cross-entropy sobre chosen tokens          → ancla el formato en cada step
L_OR  = −log σ( log[P(chosen)/P(rejected)] )       → aprende preferencia vía odds ratio
λ     = balance entre ambas pérdidas (λ = 0.1)

Sin modelo de referencia: el odds ratio entre chosen y rejected es suficiente.
L_SFT previene que L_OR desvíe al modelo de la distribución estructurada.

KTO — Kahneman-Tversky Optimization

KTO (Ethayarajh et al., 2023) es el único método probado que no requiere pares chosen/rejected. Cada muestra se etiqueta independientemente como deseable o indeseable, basándose en la prospect theory:

L_KTO_d = 1 − σ( β·(log[Pθ/Pref] − z_ref) )   ← muestras deseables (label=True)
L_KTO_u = 1 − σ( β·(z_ref − log[Pθ/Pref]) )   ← muestras indeseables (label=False)

z_ref = KL(Pθ || Pref)   ← divergencia KL como punto de referencia

Dataset: 980 positivos (ground-truth SFT) + 980 negativos (rejected DPO v2)
Sin pares — cada muestra es independiente.

A pesar de que las señales de training eran aparentemente saludables (rewards/margins=+8.5, loss=0.16), KTO colapsa completamente en formato. La causa es la misma que en DPO pero amplificada: sin L_SFT que ancle el formato y sin comparación directa de pares en el batch, el modelo aprende a distinguir bueno/malo en el espacio de rewards pero pierde la estructura. El único indicador positivo: Verb-ok%=28.6% — el modelo conoce los comandos kubectl pero no puede expresarlos en el formato requerido.

Conclusión experimental: KTO confirma que el ancla continua de formato (L_SFT en ORPO) es el factor determinante para evitar el colapso en SLMs pequeños de generación estructurada. Ningún método basado únicamente en preferencias (DPO, SimPO, KTO) logra mantener el formato sin esta señal explícita.

⭐ Agente Híbrido ReAct — Experimento 10

El trade-off Parse%/Keyword% observado en todos los experimentos anteriores no es un límite del enfoque — es consecuencia de intentar resolver ambos objetivos con un único modelo entrenado en un dataset pequeño. La solución: separar los roles.

Hipótesis: un modelo base (sin fine-tune) sigue instrucciones nuevas sin restricciones de formato; un modelo fine-tuneado tiene dominio K8s y formato garantizado. Combinados en pipeline, resuelven simultáneamente lo que ninguno logra por separado.

Auto-Remediación con Human-in-the-Loop

DevOps junior autónomo — actúa, verifica y escala con contexto completo

El diagnóstico sin acción automatiza solo la mitad del flujo de un SRE. La extensión natural del Hybrid ReAct Agent es un loop de remediación que actúa sobre el diagnóstico, verifica el resultado y escala cuando se necesita intervención humana. La pregunta clave no es si automatizar, sino cuánto automatizar de forma segura.

Analogía: un DevOps junior que hace lo que sabe hacer con seguridad (reiniciar pods, escalar réplicas) y pregunta al senior cuando no está seguro (cambiar límites de memoria, modificar configuración). Nunca borra la base de datos solo.

Grafo de Conocimiento de Remediación

Memoria ejecutable multi-paso — planes verificados por outcome y consolidados en los pesos del modelo

La auto-remediación mapea un diagnóstico a un comando kubectl. Pero los fallos reales suelen necesitar una secuencia —investigar → identificar → arreglar → verificar— y un solo comando rara vez los resuelve: un 5xx de ingress no se arregla reiniciando el controlador si el backend no tiene endpoints Ready o una NetworkPolicy bloquea el tráfico. La extensión es una memoria no-paramétrica, estructurada y ejecutable: un grafo de planes de remediación. Es el espejo del ciclo de aprendizaje del SLM, pero para la remediación en vez del diagnóstico — memoria rápida y determinista (el grafo) + consolidación lenta en los pesos (ORPO sobre diagnósticos verificados).

Diseño estilo AST (capa abstracta + binding): el nodo es una firma abstracta de problema (intent + clase de workload), portable entre clusters; la arista es un paso de remediación con plantilla de acción ({ns}, {pod}, {workload}, {service}, {pvc}, {node}), riesgo y origen. El binding (namespace y recursos reales) se resuelve en runtime con los mismos extractores deterministas del resto del sistema. La recuperación la hace código (detección de intención + lookup, con fallback por embedding), nunca el SLM — el modelo pequeño jamás carga el grafo en su contexto.

Las cinco fases

FaseQué añadeCómo
1 — SiembraCero regresiónSiembra 11 planes del catálogo existente (idempotente); el grafo arranca lleno con todo lo que el sistema ya sabía hacer.
2 — EscaladoPlanes para problemas novedososEn miss, un modelo grande (pluggable: Anthropic/OpenAI/Ollama, off por defecto) propone un plan en JSON; se valida (solo verbos de lectura + rollout restart; destructivos rechazados) y se persiste como provisional con embedding para reusarlo.
3 — VerificaciónSeñal gratis por outcomeCuando un incidente cuyo plan vino del grafo llega a estado terminal, sus aristas se marcan verificadas (resuelto+aprobado) o se registra el fallo. Misma señal que el loop de aprendizaje de RCA.
4 — ConsolidaciónConocimiento → pesosExporta a ORPO solo los diagnósticos verificados por el grafo. No reentrena soluciones (eso lo sirve el grafo, determinista y auditable); solo la prosa de diagnóstico, etiquetada por causas que la remediación confirmó.
5 — EvalMétrica de cobertura/correcciónEvaluación determinista en memoria sobre los 14 escenarios del proyecto.

El catálogo determinista da un plan con intención correcta y namespace enlazado para todos los escenarios (NS-ok 100%). La cobertura multi-paso es ~50% por diseño: el ~43% de clases con arreglo reversible dentro del cluster (config, secret, probe, OOM, red, readiness) se resuelve entero en el catálogo (investigar → rollout restart); el resto (pull de imagen, presión de nodo, binding de PVC, CPU insuficiente, auth de registry) devuelve solo investigación y se deriva al planner agéntico, que investiga en vivo y emite un comando de configuración concreto (set image/set resources/scale) si existe, o —para los arreglos genuinamente externos (crear un secret, provisionar un PV, añadir un nodo)— deja el plan de investigación más una nota "requiere acción externa". Ningún paso es un checkbox manual: el catálogo aporta la investigación, el modelo grande aporta la acción concreta en la cola larga.

Planner agéntico — el modelo grande investiga el cluster en la cola larga

Cuando un fallo novedoso no encaja en el grafo (miss del catálogo y del vecino por embedding), entra el escalado agéntico (ESCALATION_MODE=agentic, modo por defecto en producción). En vez de una llamada ciega, un modelo de código local más grande —qwen2.5-coder:14b— ejecuta un bucle ReAct que investiga el cluster en vivo (THOUGHT → ACTION con kubectl read-only → OBSERVATION) y luego emite el plan usando los nombres reales de recurso que ha observado, eliminando los placeholders <pod>/<deployment> que produce una llamada ciega. El plan validado se persiste como provisional en el grafo, listo para reusarse y para verificarse por outcome.

On-demand sobre la A30, sin romper la tesis de determinismo: el coder de 14B se carga bajo demanda en la misma A30 donde reside el experto k8s-rca-orpo (≈2 GB): ante un miss, Ollama lo carga (≈15 GB, ambos al 100% GPU, ~7 GB de margen), planifica y se descarga tras el periodo de inactividad — así el coste VRAM en estado estacionario es solo el experto pequeño. El diagnóstico sigue en el experto pequeño CPU-viable; el modelo grande solo actúa en la cola larga (problemas que el catálogo/grafo no cubren), produciendo un plan auditable, enlazado a nombres reales, read-only → reversible, en vez de una respuesta libre.

Un miss real en producción generó, para un CrashLoopBackOff de inventory-api, un plan de cinco pasos (get pods → describe pod inventory-api-64b5b587c9-4dlnb → logs → get events → rollout restart deployment/inventory-api) con el nombre real del pod resuelto y sin ningún verbo destructivo — visible ahora en la vista Grafo bajo el filtro escalado (agéntico), a la espera de verificación por outcome.

Conclusión: el sistema consolida ahora las dos mitades de un incidente —el diagnóstico (RCA, vía ORPO) y la remediación (vía el grafo)— cada una respaldada por la misma señal gratuita, verificada por outcome y con humano en el bucle. El planner agéntico rellena la cola larga del grafo sin contaminar la ruta de diagnóstico determinista.

Consola Operativa y Capacidades Extendidas

Más allá del núcleo detección→diagnóstico→remediación, todo sobre acceso read-only a la API de Kubernetes — sin Loki, sin Prometheus, sin agentes

El sistema creció hasta una consola web (FastAPI + WebSocket) de cinco vistas navegables. Toda la recopilación de datos usa el cliente Python nativo; la investigación y la remediación usan la CLI kubectl restringida a verbos de solo lectura. La única excepción es la acción de escritura aprobada por el operador (un rollout restart reversible), tras modo sombra y aprobación explícita. Nada se despliega dentro del cluster: el sistema permanece portable y sin infraestructura.

Doble fuente de detección — eventos + logs de aplicación

La detección consumía solo Eventos de Kubernetes (señales del plano de control), que son escasos: un cluster sano emite muy pocos. Se añadió una segunda fuente, los logs de aplicación (read-only, acotado por since_seconds/tail_lines/max_pods), que alimenta el mismo Drain3 + Isolation Forest. Captura señal a nivel de app (errores, trazas, fallos de init) que nunca genera un evento K8s. En el cluster de producción, activar logs elevó la señal por ventana de 1-2 eventos a 600+ líneas en 34 namespaces.

Vista Grafo y ejecución paso a paso

La vista Grafo hace inspeccionable el grafo de conocimiento de remediación: cada nodo es una tarjeta plegable con la firma del problema (intent + clase de namespace), un badge de origen (catálogo vs escalado agéntico), el estado de verificación (✓ éxitos/intentos) y, al desplegar, el plan multi-paso completo con tipo, riesgo (L0–L3) y comando enlazado. Un filtro separa los planes sembrados del catálogo de los que el planner agéntico ha aprendido, para ver crecer el conocimiento del sistema. En Incidencias, cada paso ejecutable tiene su propio botón play con estado en vivo derivado del log de ejecución (▶ Ejecutar → ⟳ Ejecutando… → ✓ Hecho), y un paso manual bloquea los posteriores hasta que el operador lo confirma.

Nota (versión final): una versión anterior exponía un agente conversacional ("chat con el cluster"). Se eliminó: el diagnóstico con experto único más el planner agéntico cubren la misma necesidad de investigación pero actúan —producen planes verificables que rellenan el grafo— en vez de devolver prosa. El toolbox read-only que usaba permanece, reutilizado por el planner agéntico y por el ejecutor paso a paso.

Escáner de seguridad — del fallo operativo al riesgo de seguridad

El mismo enfoque read-only se extiende a la postura de seguridad con ~10 checks deterministas basados en reglas: contenedores privilegiados, runAsRoot, hostNetwork/hostPath, capabilities peligrosas, imágenes con tag mutable, secretos en variables de entorno, sin límites de recursos, bindings a cluster-admin y namespaces sin NetworkPolicy. Cada hallazgo lleva severidad y recomendación concreta.

Reglas, no LLM (a propósito): la detección de seguridad debe ser determinista, auditable y sin alucinaciones — igual que trivy/kubescape. El LLM aporta valor después: contextualiza y prioriza (distingue un CNI legítimamente privilegiado de un pod de aplicación sospechoso). En el cluster real surgieron 353 hallazgos (31 críticos) en menos de un segundo, sin instalar nada.
Tesis: el mismo pipeline de investigación read-only que diagnostica anomalías operativas audita también la postura de seguridad — sin GPU en inferencia y sin desplegar agentes en el cluster.

Tracking con MLflow

Trazabilidad completa del pipeline de detección y del proceso de fine-tuning

El pipeline registra automáticamente cada ejecución en MLflow. Se crearon dos experimentos separados para mantener el tracking del modelo y del sistema de detección desacoplados.

ExperimentoQué se registra
k8s-aiops Un run por ejecución del pipeline. Params: configuración inicial completa. Métricas por step: score, is_anomaly, log_count, template_count, pca_x/y. Por cada reentrenamiento IF: model_version, training_size, n_features. Por cada RCA: anomaly_score, latency_s, root_cause y kubectl como tags.
k8s-aiops-finetune Run único con historial completo del entrenamiento QLoRA: 18 hiperparámetros, curva de loss/lr/grad_norm por step (10→180), métricas finales y tags de trazabilidad al modelo en HuggingFace.
La integración es opcional y no intrusiva: si MLflow no está disponible o MLFLOW_ENABLED=false, todas las llamadas son no-op y el pipeline funciona con normalidad.

Reproducir el fine-tuning desde cero

# 1. Clonar el repositorio
git clone https://github.com/aaranda233/k8s-aiops && cd k8s-aiops

# 2. Construir la imagen Docker (requiere GPU NVIDIA, CUDA 12.4+)
docker build -t k8s-rca-finetune finetune/

# 3. Lanzar el entrenamiento (~8 min en A30 24 GB)
docker run --gpus all --rm \
  -v $(pwd)/finetune/output:/workspace/output \
  k8s-rca-finetune python train.py \
  --dataset output/combined.jsonl --epochs 3

# 4. Registrar el modelo en Ollama
ollama create k8s-rca-slm -f finetune/Modelfile
