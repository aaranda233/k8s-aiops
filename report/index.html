📄 Resumen Ejecutivo

Motivación, contribución y diferencial del trabajo

Las plataformas Kubernetes en producción generan miles de eventos por minuto. Identificar cuándo un patrón de logs indica un fallo real — y diagnosticar su causa raíz de forma automática — es uno de los problemas no resueltos del Site Reliability Engineering moderno.

Las soluciones comerciales existentes (Dynatrace, Datadog, New Relic) resuelven el problema, pero envían los datos del cluster a servidores externos. Esto las hace inviables para entornos con requisitos de privacidad o regulaciones de datos.

Este trabajo presenta un pipeline AIOps completamente local que combina:

📡 Capa 1 — Colección y Parsing de Logs

Watch API de Kubernetes + Drain3 para parsing online de templates

Watch API

A diferencia del polling periódico, la Watch API de Kubernetes mantiene una conexión HTTP chunked abierta indefinidamente. El API Server escribe un objeto JSON por línea conforme ocurren eventos en el cluster, sin necesidad de que el cliente vuelva a preguntar.

El campo resourceVersion actúa como cursor de posición en el stream. Si la conexión se interrumpe, el colector reconecta usando el último resourceVersion conocido, garantizando entrega at-least-once sin perder eventos.

# Ejemplo de evento recibido por Watch API
{
  "type": "ADDED",
  "object": {
    "reason": "BackOff",
    "message": "Back-off restarting failed container nginx in pod nginx-7d4f9c-xp2lm_production",
    "involvedObject": { "namespace": "production", "name": "nginx-7d4f9c-xp2lm" },
    "metadata": { "resourceVersion": "1847392" }
  }
}

Drain3 — Parsing Online de Templates

Los mensajes de log de Kubernetes contienen tokens variables (IPs, UUIDs, nombres de pods, números de restart). Drain3 agrupa logs semánticamente similares en templates, reemplazando los tokens variables por <*>.

Algoritmo

Árbol de prefijos con profundidad 4. Similitud calculada como tokens coincidentes / tokens totales ≥ 0.4

Output

Cada log produce un cluster_id entero que identifica su template. Este ID es el feature del detector

Online

No requiere batch previo. Los templates se crean y actualizan conforme llegan logs, sin reentrenamiento

# Raw log → Template Drain3
# Input:
"Back-off restarting failed container nginx in pod nginx-7d4f9c-xp2lm_production"
# Output:
template  = "Back-off restarting failed container <*> in pod <*>"
cluster_id = 42

🔍 Capa 2 — Detección de Anomalías

Isolation Forest no supervisado con reentrenamiento continuo

Ventanas Temporales

Los logs se agrupan en ventanas de 60 segundos. Cada ventana se convierte en un vector de frecuencias — cuántas veces apareció cada cluster_id de Drain3 en ese intervalo. El vector se normaliza con L1 para hacer la comparación invariante al volumen de eventos.

Isolation Forest

El Isolation Forest detecta anomalías sin necesidad de ejemplos etiquetados. La intuición es que los puntos anómalos son estadísticamente escasos y se aíslan con pocos cortes aleatorios en el espacio de features, mientras que el comportamiento normal (denso) requiere muchos más cortes para aislarse.

ParámetroValorJustificación
n_estimators200Balance precisión/velocidad; más árboles = menor varianza
contamination0.05Asumimos ≤5% de ventanas anómalas en operación normal
threshold0.80Score normalizado 0-1; >0.80 dispara alerta
bootstrap_windows10Ventanas iniciales para construir baseline antes de detectar
rolling_window_size50Ventanas recientes para reentrenamiento (ventana deslizante)
retrain_every_n5Reentrenar IF cada 5 ventanas nuevas (adapta al drift)

Tres Fases de Operación

1. Bootstrap

Las primeras 10 ventanas se acumulan asumiendo comportamiento normal. El modelo IF se entrena por primera vez con este baseline.

2. Detección

Cada nueva ventana se puntúa (0-1). Si score ≥ 0.80, se dispara la Capa 3 de diagnóstico.

3. Reentrenamiento

Cada 5 ventanas, el IF se reentrena con las últimas 50 (ventana deslizante). Adapta el modelo al drift sin olvidar el pasado reciente.

Adicionalmente, se aplica PCA 2D sobre el training set en cada reentrenamiento para proyectar las ventanas en un espacio visualizable, permitiendo monitorizar clusters de comportamiento en el dashboard.

🧠 Capa 3 — Diagnóstico con SLM Fine-tuneado

Qwen2.5-1.5B-Instruct con QLoRA, convertido a GGUF Q8_0 para inferencia en CPU

Selección del Modelo Base

Se eligió Qwen2.5-1.5B-Instruct como modelo base por tres razones: (1) tamaño suficientemente pequeño para inferencia en CPU a velocidad aceptable, (2) capacidad de seguir instrucciones estructuradas desde el primer momento, y (3) excelente soporte del formato ChatML que facilita el fine-tuning con datos de conversación.

Proceso de Fine-tuning (QLoRA)

El fine-tuning se realizó en una GPU NVIDIA A30 (24GB VRAM) utilizando QLoRA — cuantización 4-bit NF4 del modelo base con adaptadores LoRA entrenables sobre los módulos de atención y proyección.

HiperparámetroValor
LoRA rank (r)16
LoRA alpha32 (ratio alpha/r = 2)
LoRA dropout0.05
Target modulesq_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj
Batch efectivo16 (batch_size=4 × grad_accum=4)
Learning rate2×10⁻⁴ con cosine scheduler
Épocas3
Parámetros entrenables~5M de 1.5B (1.6%)
Duración~8 minutos en A30
Frameworkunsloth + TRL SFTTrainer

Cuantización a GGUF

Los adaptadores LoRA se fusionan con el modelo base y se cuantizan a GGUF Q8_0 (1.6GB) para inferencia con Ollama/llama.cpp en CPU. Se evaluó también Q4_K_M (941MB) pero produjo degradación severa de calidad en modelos de 1.5B — respuestas repetitivas, mezcla de idiomas y no adherencia al formato. Q8_0 es el nivel mínimo efectivo para este tamaño de modelo.

Formato de Respuesta

El modelo genera respuestas estructuradas en dos partes obligatorias:

ROOT CAUSE: [diagnóstico de la causa raíz en lenguaje natural]
KUBECTL: kubectl [comando exacto para investigar o mitigar]

Pod nginx-deployment-7d9f8b6c4-xk2lp in namespace production is in CrashLoopBackOff. Logs show: Error: ECONNREFUSED 10.96.0.1:443. The pod has restarted 8 times in the last 10 minutes.

Test 2 — OOMKilled + Memory Pressure en Nodo ⏱ 0.75s (warm) CORRECTO
Multiple pods in namespace monitoring are being OOMKilled. prometheus-0 restarted 5 times, grafana-7d4f9c-xp2lm restarted 3 times. Node kube-worker-02 shows memory pressure. kubectl top nodes shows kube-worker-02 at 94% memory.
Memory pressure en el nodo kube-worker-02. Probablemente algún pod está consumiendo más memoria de la permitida. Los pods sin PriorityClass son los primeros en ser eliminados por K8s.

📉 Tracking con MLflow

Trazabilidad completa del pipeline de detección y del fine-tuning

El pipeline registra automáticamente cada ejecución en MLflow. Se crearon dos experimentos separados:

k8s-aiops

Un run por ejecución del pipeline. Registra configuración inicial como params, y por cada ventana: score, is_anomaly, log_count, template_count, pca_x/y. Por cada reentrenamiento del IF: model_version, training_size, n_features. Por cada RCA: anomaly_score, latency_s y tags con root_cause y kubectl.

k8s-aiops-finetune

Run único con el historial completo del entrenamiento QLoRA: 18 hiperparámetros, curva de loss/lr/grad_norm por step (10→180), métricas finales y tags de trazabilidad al modelo en HuggingFace.

La integración es no-op si MLflow no está disponible — el pipeline no falla. Controlable con la variable de entorno MLFLOW_ENABLED=false.

Reproducir el fine-tuning desde cero

# 1. Clonar el repositorio
git clone https://github.com/aaranda233/k8s-aiops
cd k8s-aiops

# 2. Construir la imagen Docker (requiere GPU NVIDIA, CUDA 12.4+)
docker build -t k8s-rca-finetune finetune/

# 3. Lanzar el entrenamiento (~8 min en A30 24GB)
docker run --gpus all --rm \
  -v $(pwd)/finetune/output:/workspace/output \
  k8s-rca-finetune \
  python train.py --dataset output/combined.jsonl --epochs 3

# 4. Registrar en Ollama
ollama create k8s-rca-slm -f finetune/Modelfile

⚠️ Limitaciones y Trabajo Futuro

Puntos de mejora identificados para la versión final del paper

Sin conjunto de evaluación (eval split): El entrenamiento no reservó un subconjunto de validación. El train_loss de 0.09 no puede distinguirse formalmente de memorización sin un eval_loss de referencia. Trabajo futuro: split 80/20 con early stopping sobre eval_loss.
Sin baseline de comparación: No se midió la diferencia entre el modelo fine-tuneado y el modelo base (Qwen2.5-1.5B sin fine-tuning) sobre los mismos escenarios. Esta comparación es necesaria para cuantificar la contribución del fine-tuning y es el experimento más importante pendiente.
Dataset 100% sintético: Los 986 samples fueron generados programáticamente. Los patrones de fallo reales en producción pueden diferir de los simulados. Trabajo futuro: incorporar logs reales anonimizados del cluster.
Evaluación cualitativa limitada: Solo se evaluaron 3 escenarios manualmente. Trabajo futuro: evaluación cuantitativa sobre un held-out set con métricas de tarea (ROUGE-L sobre root_cause, exact match de verbo kubectl).
